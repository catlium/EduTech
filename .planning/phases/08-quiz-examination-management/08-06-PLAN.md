<objective>
Close two failed verification truths:
- **WR-01 (gap 2):** `updateAssessment` re-validates only the PATCHED (non-null) fields, so a PATCH that flips endsAt before startsAt (or winds startsAt into the past) sails through as the only touching field. The fix: validate the MERGED schedule (existing overlaid with the patch) on every update, with a future-startsAt requirement only when startsAt itself is patched.
- **WR-02 (gap 3):** the Create/AddQuestions DTOs accept empty payloads — `POST {}` and `POST {"title":""}` create assessments with no title, and addQuestions accepts a missing questionIds array. The fix: `@IsDefined`/`@MinLength(1)` on title, `@IsDefined`/`@IsArray`/`@ArrayMaxSize(1000)` on questionIds.

Purpose: without merged-schedule validation the schedule invariant (start < end, no past starts) is a lie the update endpoint destroys with one field; without DTO validation the API accepts structurally invalid assessments. Both are write-path trust-boundary holes (EXAM-01 create-time validity, EXAM-02 update-time validity, EXAM-04 questions-linkage validity).
Output: write-path validation enforced at both the DTO layer and the service layer, documented, and covered by 5 new E2E cases (suite PASS=65).
</objective>
